Cadrage · Lot C · ragcore

Maîtriser l'embedding, de bout en bout

Aujourd'hui les vecteurs sortent de TEI — un service qu'on subit : il impose son catalogue de modèles, et il détient le tokenizer qui devrait faire autorité pour le chunker. Le Lot C reprend ce contrôle sans alourdir le pipeline : un service d'embedding qu'on écrit et qu'on héberge, derrière la frontière que ragcore a déjà posée.

§C.0

Pourquoi un lot, et pas un correctif

archi

Le « point 3 » du bilan — faire compter le chunker en tokens plutôt qu'en caractères — semblait une tâche isolée. Il ne l'est pas. Son tokenizer d'autorité, celui qui doit dire « ce chunk fait 300 tokens », est celui qui embed réellement. Tant que l'embedding vit dans un service tiers dont on ne choisit ni le modèle ni la révision, ce tokenizer est hors de portée : l'aligner sur TEI reviendrait à figer une correspondance qu'un simple changement d'image casserait en silence.

La question du chunker et la question du service d'embedding sont donc la même question par deux bouts — exactement comme le nommage de collection et la config de workflow l'étaient au §6. On les traite ensemble.

Le vrai verrou n'est pas « écrire un embedder ». Il existe déjà — LocalEmbedder, OpenAIEmbedder, NoopEmbedder, tous derrière le port BaseEmbedder. Le verrou est de qui dépend le tokenizer d'autorité. Constat mesuré le 15 juillet — la porte était déjà entrebâillée.
§C.1

Ce dont on part — l'acquis, mesuré

archi

Le port BaseEmbedder a été écrit dès l'origine pour « un service distant ou un modèle local ». Trois implémentations le respectent déjà, et le hook choisit entre elles. Le fingerprint (§6) dérive de model_name + dimension — un changement de modèle produit déjà une collection distincte. Rien de tout cela n'est à inventer.

Acquis — ne rien réécrire

  • La frontière est bonne. BaseEmbedder.embed() est asynchrone, par lots, et ignore où le calcul se fait. Le reste du pipeline ne verra pas la bascule.
  • Le fingerprint couvre déjà le modèle. Deux modèles ⇒ deux empreintes ⇒ deux collections. L'A/B entre modèles est gratuit.
  • Le garde-fou d'alignement existe. assert_service_serves_model refuse d'écrire si le service ne sert pas le modèle dont le nom baptise la collection. Ce contrat survivra au changement de service — il change juste d'interlocuteur.
§C.2

La cible d'exécution — un service qu'on contrôle

archi

Deux voies mènent à l'autonomie : rapatrier le calcul dans le process d'ingestion (LocalEmbedder, sentence-transformers en mémoire), ou garder l'architecture service HTTP mais remplacer TEI par un service maison dont on choisit les modèles.

Tranché — service maison, pas in-process

On garde le port et son client HTTP (OpenAIEmbedder), et on remplace l'implémentation derrière l'URL. La lourdeur — torch, les poids des modèles — reste isolée dans le service ; l'environnement d'ingestion ne gagne aucune dépendance (il parle déjà httpx).

Ce choix sert directement l'objectif du lot — le moins de dépendances possible dans le pipeline — tout en levant la contrainte de TEI : le service étant à nous, son catalogue de modèles est le nôtre.

Reste ouvert — la forme du service

Cadre non figé : quel socle sert les modèles (un petit serveur sentence-transformers maison ? un runtime ONNX pour se passer de torch au service ?), quel contrat d'API au-delà de /embeddings et /tokenize, et comment le service déclare le modèle qu'il sert (le garde-fou /info attend déjà un model_id).

§C.3

Le tokenizer d'autorité — résolu par construction

archi

C'est ici que le lot rembourse sa dette. Puisque le service est à nous, on lui fait exposer un endpoint /tokenize qui rend, pour chaque token, ses bornes en caractères (offsets). Le chunker consomme ces offsets — il découpe en tokens mais lit char_start / char_end dans les positions littérales du contenu.

Le tokenizer qui compte les tokens du chunk est, par construction, celui qui embed le chunk. Le décalage qu'on cherchait à supprimer ne peut plus exister — il n'y a plus deux tokenizers à désaligner.

Tranché — décisions héritées de la discussion du 15 juillet

  • Tokeniser avec offsets, jamais re-décoder. Le texte re-décodé peut différer de l'original (espaces, normalisation) ; les offsets redeviendraient faux, et l'invariant durement acquis du chunker (chaque section est un morceau littéral du contenu) tomberait.
  • Un port TokenCounter injecté. Le chunker reste pur et synchrone, testable avec un fake trivial ; l'adapter concret interroge le service. Cohérent avec l'hexagonal du reste de ragcore.

Le piège qu'on ferme

Le chunker compte aujourd'hui en caractères, la fenêtre du modèle en tokens ; le ratio va de 3,08 car/token en moyenne à 0,33 au pire (sigles, ponctuation). Aucune valeur en caractères n'est sûre par construction. Le fallback par dichotomie de l'embedder rattrape le débordement — il ne le supprime pas. Le §C.3 supprime la cause.

§C.4

Le fingerprint — le tokenizer suit le modèle

archi

Faut-il ajouter le tokenizer au hash de workflow, pour qu'un changement force une nouvelle collection ? La question, brûlante avec TEI, s'éteint d'elle-même ici : le service sert un modèle, et le tokenizer est celui de ce modèle. Ils ne peuvent pas diverger. Le fingerprint dérive déjà de model_name — il couvre donc déjà le tokenizer, sans champ nouveau.

Reste ouvert — à trancher à l'implémentation

Le seul cas résiduel : deux révisions du même nom de modèle qui tokenizeraient différemment. Le garde-fou /info peut être étendu pour exposer une révision, et le fingerprint la lire — décision à prendre si et quand ce cas se présente, pas avant.

§C.5

Les livrables du lot

Dans l'ordre de dépendance — chacun débloque le suivant.

  1. Le service d'embedding maison — sert les modèles qu'on choisit, expose /embeddings, /tokenize (avec offsets) et /info. La lourdeur y est confinée ; le pipeline ne parle que HTTP.
  2. Le port TokenCounter + son adapter — abstraction pure côté chunker, client HTTP côté adapter. Un fake pour les tests unitaires.
  3. Le chunker compte en tokens — « l'ex-point 3 » : fenêtrage sur les tokens, bornes lues dans les offsets. La cause du débordement disparaît ; le fallback de l'embedder devient une ceinture, plus la seule protection.
  4. Bascule du hook sur le service maison — OpenAIEmbedder pointe sur la nouvelle URL ; assert_service_serves_model valide l'alignement modèle ↔ collection contre le nouveau /info. Aucun nœud du DAG ne bouge.
§C.6

Ce que le lot ne fait pas

Hors périmètre — pour ne pas gonfler le lot

  • Ce n'est pas devant le produit. Le point qui bloque le serving reste le pointeur de collection côté backend — indépendant de l'embedding. Le Lot C ne le remplace pas dans la file.
  • Ce n'est pas la mesure de pertinence. Choisir un modèle d'embedding « meilleur » suppose un jeu de questions de référence qui n'existe pas encore. Le lot rend ce choix possible (n'importe quel modèle) ; il ne tranche pas lequel.
  • Ce n'est pas le lot B. Registre d'alias, MLflow, backends typés — dette de doctrine distincte, intacte.
