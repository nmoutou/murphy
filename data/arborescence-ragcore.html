ragcore · arborescence cible · rév. 3 — arrêtée

La doctrine, traduite en modules

Chaque décision du cadrage a désormais un fichier où elle vit. Cette carte n'invente rien : elle place les treize familles dans l'hexagone, et dit pour chaque module s'il existe déjà, s'il est à réécrire, ou s'il reste à écrire. Les trois arbitrages de placement sont tranchés ; l'arborescence des tests et la scission des deux configs y sont entrées.

État réel du dépôt — à savoir avant de lire

hooks.py importe aujourd'hui une quinzaine de modules absents de l'arbre (adapters/embedding/*, les client.py de chaque store, audit_repository, run_summary_repository, config/settings.py, pipeline_context, ports/telemetry.py, file_connector, pipeline_registry). C'est la trace de la récupération partielle déjà consignée. Ces modules sont donc marqués à écrire — non parce qu'ils sont neufs, mais parce qu'il n'y a rien à lire dans le dépôt. Le code perdu, s'il ressort, sera un point de départ, pas une contrainte.

Ce que l'arborescence dit, que la doctrine ne disait pas encore

Traduire en modules force trois arbitrages que le texte pouvait laisser flous.

  • sources/generic/ est le vrai lieu de §3. La doctrine disait « un parser générique + stratégies enfichables » sans dire où vit le générique. Le mettre dans sources/ et non dans core/ est délibéré : parser, c'est traduire un format extérieur — c'est un adaptateur d'entrée, pas du domaine. core/links, lui, est du domaine : un lien juridique existe indépendamment du XML qui le porte. D'où le partage : le parser appelle core/links, jamais l'inverse.
  • Il ne reste presque rien de sources/legi/. Trois de ses cinq modules disparaissent, absorbés. Ce qui subsiste — une table de rôles et quatre handlers — tient dans un fichier. C'est la mesure du succès de §3 : si ajouter la jurisprudence coûtait un second parser.py, la doctrine aurait échoué. Ici, une source nouvelle = une table.
  • Le port runtime.py vit dans core/, pas dans utils/. Ce n'est pas un détail de rangement. Tant que le pont sync↔async était une fonction utilitaire sur une global, il n'était le contrat de personne. En faire un port du domaine, c'est déclarer que le modèle de concurrence est une décision d'architecture — exactement ce que §11 exige.

Les quatre contrats neufs

§11 §13 §9 §1

Le reste est du déplacement. Ces quatre-là sont ce que le cadrage a réellement créé.

# core/ports/runtime.py — §11, invariant 1
class AsyncRuntime(Protocol):
    def run(self, coro: Coroutine[Any, Any, T]) -> T: ...
    def drain(self) -> None: ...          # at-least-once aux frontières
    def close(self) -> None: ...
    # une instance = une boucle + son lot de clients. Rien de partagé.

# core/ports/telemetry.py — §11, la fabrique
class TelemetryFactory(Protocol):
    def build(self, runtime: AsyncRuntime) -> TelemetryPort: ...
    # le hook ne peut plus construire UNE instance : il y a N workers.

# core/ports/pending_repository.py — §13, le rejeu ciblé
class PendingRepository(Protocol):
    async def remember(self, pending: PendingRelation) -> None: ...
        # union idempotente : absent → insert(first_seen_run)
        #                    présent → update(last_seen_run)
    async def promotable_for(
        self, owner_id: OwnerId, new_node_ids: set[CanonicalKey]
    ) -> list[PendingRelation]: ...
        # ← borné par le DELTA de la run, jamais par le backlog.
        #   C'est CE contrat qui rend le TTL inutile.
    async def forget(self, promoted: list[PendingRelation]) -> None: ...

# core/ports/alias_registry.py — §1, l'inventaire lisible
class AliasRegistry(Protocol):
    async def resolve(self, alias: str, owner_id: OwnerId) -> CanonicalKey | None: ...
    async def append(self, key: CanonicalKey, aliases: list[str]) -> None: ...
    async def list_known(self, owner_id: OwnerId) -> set[str]: ...
        # acté en v0 bien que le pipeline binaire ne le consomme pas.

Lire promotable_for comme la clé de voûte. C'est la signature qui rend vraie la doctrine du cache : parce que le rejeu est borné par les nœuds neufs et non par le backlog, une pendante ancienne ne coûte rien — et c'est pour cette raison qu'aucun TTL n'est nécessaire. Le contrat n'illustre pas la décision : il en est le mécanisme.

Deux configs, deux couches

§6 §9

Ce qui change le résultat vit dans le domaine. Ce qui ne le change pas vit dans l'infra. La frontière est celle du hash.

Le pipeline a besoin de deux sortes de réglages, et ils sont aujourd'hui mélangés dans un settings.py unique.

  • Ceux qui changent le résultat. chunk_size, chunk_overlap, le modèle d'embedding, la norm_version. En changer un : les vecteurs produits ne sont plus les mêmes. Les anciens et les nouveaux ne sont plus comparables — ils ne peuvent pas cohabiter dans une collection.
  • Ceux qui ne changent rien. MONGODB_URI, le mot de passe Neo4j, le chemin source, le nombre de workers, le dossier des logs. Déménage Mongo sur une autre machine : les vecteurs produits sont identiques. C'est le où et le comment, pas le quoi.

Pourquoi c'est structurel, et pas du rangement. §6 a décidé que le nom de la collection Qdrant est un hash de la config — c'est ce qui rend l'A/B possible. Mais alors : hash de quoi ? Si le hash mange toute la config, il mange l'URI Mongo. Passe de localhost au conteneur Docker : le hash change, une collection neuve est créée — alors que tu produis rigoureusement les mêmes vecteurs. L'A/B est perdu pour une raison qui n'a aucun sens, et le même run rejoué depuis deux machines n'atterrit pas au même endroit.

D'où la scission : WorkflowConfig dans core/config/, InfraSettings dans adapters/config/. La fonction fingerprint() vit dans core/ et ne voit que le premier — elle n'a physiquement pas accès à l'URI Mongo. L'erreur devient impossible par construction, au lieu d'être évitée par la discipline de qui pense à exclure les bons champs au moment de hasher. C'est exactement la forme d'argument que le principe directeur d'architecture réclame : une garantie, pas une convention.

Cas limite qui prouve que la frontière est nette : RETRIEVAL_TOP_K n'est ni l'un ni l'autre — c'est du serving, il n'appartient pas à ragcore.

Le DAG bi-phasé

§11

La barrière n'est pas un join() : c'est une arête. Elle se lit dans kedro viz.

  connect ──► compute_idempotence ──► ingest_documents ──┬──► resolve_relations ──► report
                                       │ IngestionRunner      │          │ phase 2
                                       │ N workers            │          │ relations en batch
                                       │ 1 AsyncRuntime chacun │          │ + cache pendantes
                                       │ saga 3 steps / doc    │
                                       └─ sort : RunStats ─────┘
                                                              ▲
                                            cette arête EST la barrière
                                     tous les nœuds avant toute arête (§11)
  • Le hook cesse d'être un lieu de logique. Aujourd'hui after_pipeline_run finalise l'agrégateur — il calcule. Demain il ne voit plus les workers : il ne peut plus. La fusion redescend dans le node, l'agrégat sort comme donnée, et hooks.py redevient ce qu'il aurait toujours dû être : du câblage.
  • Le pool est testable sans Kedro. IngestionRunner ne connaît ni DataCatalog, ni hook_impl. On peut le lancer depuis un test, un CLI, un service. Le modèle de concurrence n'est pas prisonnier de l'orchestrateur — ce qui est précisément l'argument qui a fait rejeter les runners Kedro.

Ce qui meurt

§10

Sept modules. Aucun n'est un accident : chacun est une doctrine qui a changé.

  • utils/async_utils.py — la global _LOOP. État mutable partagé au niveau module. Toute la §11 est, au fond, la mise à mort de cette variable.
  • legi/parser.py, legi/chunking.py, legi/relations.py. Absorbés. Le parser LEGI n'extrait aucun lien aujourd'hui ; relations.py travaille en aval sur un ParsedDocument. core/links renverse ça : l'extraction se fait à la balise, là où le sens et le type sont encore lisibles.
  • nodes/persist.py. Un node qui persiste, c'est la persistance hors de la saga du worker. Contradictoire avec §8.
  • telemetry/composite.py. Fichier vide ; le registry a pris le rôle.
  • Et hors ragcore : data/src/data/pipelines/embedding/. Le node archivé que le CLAUDE.md signale déjà comme mort. Le supprimer, pas le maintenir.

Pourquoi les tests ont quatre lieux

§3 §6 §9 §12

Ce n'est pas un rangement par commodité : chaque dossier correspond à une nature de vérification différente.

  • golden/ est séparé parce que ce ne sont pas des tests : ce sont des cliquets. Un test unitaire échoue quand tu casses le code. Un golden échoue quand tu changes la doctrine sans t'en rendre compte. Le cadrage l'a exigé trois fois — « balise sans rôle casse le build » (§3), « event inconnu = échec » (§12), « même config → même hash, pour toujours » (§6). Ce sont des engagements, pas des vérifications. Les noyer dans unit/ les banaliserait : un jour, quelqu'un mettrait à jour le fichier attendu pour faire passer le build. Isolés dans golden/, y toucher est un geste visible en revue — c'est précisément l'effet recherché.
  • contract/ existe parce que tu as des ports. Un test de contrat est écrit contre le port, pas contre l'adapter : le même test tourne sur MongoPendingRepository et sur un InMemoryPendingRepository. C'est la preuve exécutable que la substituabilité promise par l'hexagone est réelle. Sans lui, « adapter interchangeable » est une intention, pas un fait — et le jour où MLflow cède la place à ClearML (§9 le prévoit), c'est ce test qui dira si le nouvel adapter est conforme.
  • fixtures/corpus/ est le pont avec la saturation. §3 attend analyze(corpus_complet) sur les cinq arbres. Le corpus qui sature la table de rôles est celui qui alimente les golden d'ingestion. Une seule copie : deux corpus qui divergent, c'est un golden qui atteste d'une doctrine que le pipeline n'applique plus.
  • integration/ reste mince. Deux fichiers, pas vingt : la compensation Neo4j exacte et la barrière bi-phasée. Ce sont les deux endroits où seule une vraie base peut dire la vérité — le reste se teste contre les ports.
  • Et il tourne sur testcontainers, pas sur le docker-compose. Le motif n'est pas le confort : c'est que docker-compose ferait tester contre une base qui a déjà servi. Or ces deux tests sont exactement ceux où l'état résiduel ment — test_saga_rollback vérifie qu'après compensation il ne reste rien ; un nœud laissé par un run précédent le fait passer ou échouer sans rapport avec le code. Un état vierge donne un verdict qui veut dire quelque chose. Et en CI, il n'y a pas d'alternative. Conséquence de conception : Neo4j démarre en plusieurs secondes ⇒ containers scopés session, isolation rétablie par drop des bases entre tests — tenable précisément parce que ces tests sont peu nombreux par conception.

L'arborescence est arrêtée — place au code

Les quatre arbitrages sont tranchés : sources/generic/ (le parser est un adaptateur d'entrée) ; ragcore/tests/ centralisé, en quatre natures ; la scission WorkflowConfig / InfraSettings ; et l'intégration sur testcontainers. Plus aucune question de structure n'est en attente.

L'ordre d'écriture suit les dépendances — et il n'est pas arbitraire : chaque couche ne peut être écrite que parce que la précédente a figé ce dont elle a besoin.

  1. core/ — modèles, ports, links, fingerprint, WorkflowConfig. Tout en dépend, rien n'en dépend. C'est ici que la doctrine devient du code ; les golden de fingerprint et de normalisation se posent en même temps.
  2. application/ — saga à 3 steps, IngestionRunner, ResolveRelationsService. Testable sans aucune base : les ports suffisent.
  3. adapters/ — les stores, le runtime asyncio, la télémétrie, MLflow. Les tests de contrat écrits à l'étape 1 les valident en arrivant.
  4. sources/generic/ + legi/strategy.py — le parser et sa première table de rôles. La saturation (§3) peut alors tourner.
  5. Le shell Kedro — en dernier, quand il n'a plus qu'à câbler. Si à ce stade il contient de la logique, c'est que quelque chose s'est mal passé en amont.
