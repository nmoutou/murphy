ragcore · doctrine de refonte · v0 — rév. 10

La doctrine d'ingestion, tranchée famille par famille

Refonte du pipeline à l'occasion du passage de la législation (LEGI) à la jurisprudence (CAPP, CASS, CONSTIT, INCA, JADE). Ce document n'inventorie plus des questions ouvertes : il fige la doctrine décidée et n'isole que les rares points encore ouverts. On reste en cadrage jusqu'à ce qu'aucune zone d'ombre ne subsiste.

Principe directeur — métier

Communaliser au maximum, se simplifier la vie au maximum.

Un seul parser générique (+ quelques stratégies enfichables), pas cinq. Pas de typage métier — le « type de fichier métier » est un simple champ. La différenciation se joue entre les bases (Mongo = texte + méta, Neo4j = méta + liens + registre d'identité), pas dans une hiérarchie de types Python. On ingère brut : pas de lemmatisation, pas de linéarisation en v0 — mais une normalisation typographique de surface. Ce qui n'est pas encore résolu n'est pas un état spécial — c'est un node unknown qui attend sa passe de résolution.

Principe directeur — architecture (chapeaute tout)

L'architecture est le socle sain de tout le reste : propre à toutes les versions, v0 comprise — jamais « propre plus tard ».

Le tempo v0 (drop-&-rejoue, idempotence binaire, delta repoussé) ne concerne que le fonctionnel — ce que le pipeline produit. Il ne s'applique jamais à la forme du code : ports, contrats, modèle de concurrence, frontières hexagonales naissent propres et le restent. On applique les bons principes de conception — responsabilités nettes, extensibilité, robustesse, substituabilité — sans concession de tempo. Une hypothèse d'exécution (mono-thread, sémantique de livraison) est déclarée, jamais implicite ; une dégradation est observable, jamais silencieuse. Ce principe surplombe les familles métier autant que les familles d'architecture.

Rév. 10 — cette passe : cohérence interne, aucune décision nouvelle. Le cadrage était clos mais se contredisait en trois points, tous hérités de révisions antérieures que les suivantes n'avaient pas repropagées. (1) §9 disait encore « Parsing → Résolution → Persist » — l'ordre de la rév. 5, inverse de celui que §11 a tranché en rév. 7-8 : dans le DAG bi-phasé, la persistance des nœuds précède la résolution des arêtes, et il n'y a pas d'étape Persist terminale (elle vit dans la saga du worker — d'où la mort de persist.py). §9 porte désormais le DAG réel. (2) §10 et §12 gardaient un « reste ouvert » nu, qui se lisait comme une décision en attente alors que le document affirme n'en avoir aucune. Ce n'en sont pas : ce sont des mesures (le seuil du « livrable » se lit sur des golden sets peuplés ; la liste des events de dégradation dérive de la saturation §3). Requalifiés comme tels — la distinction « décision en attente » vs « mesure à faire tourner » est désormais portée par la légende, plus par le lecteur.

Rappel rév. 9 : §13 fermée — pas de TTL (il confondrait « non résolue » et « invalide », et casserait la convergence), clé (owner_id, source_id, target_id, relation_type), union idempotente, retry_count abandonné. — Rév. 8 : §11 fermée — Kedro exprime les phases, ragcore possède les workers (la barrière est une arête du DAG) ; agrégats fusionnés dans le node ; télémétrie en fabrique ; audit at-least-once ; rejeu ciblé. — Rév. 7 : worker pool sans verrou par conception, ingestion bi-phasée, famille §13. — Rév. 6 : tags métier / archi, second principe directeur, lab §3 tranché.

Doctrine tranchée Déjà stable dans le code Reste ouvert — et de quelle nature : v1 (hors périmètre, daté) · mesure (un travail de terrain, pas un arbitrage) · hors-ragcore (autre chantier). Aucun n'est une décision de cadrage en attente. métierfamille de domaine juridique archifamille d'infrastructure (transverse à toute source)
01

Acquisition & provenance

métier

Comment les documents entrent, d'où, et sous quelles formes.

Doctrine tranchée

  • Pipeline off-line, pas live. Ingestion & mise à jour de documents juridiques, jouée hors-ligne (schédulée à terme pour les MAJ). Les documents utilisateur sont traités ailleurs, pas dans ce pipeline.
  • Formats multiples côté source. XML DILA aujourd'hui, mais .odt, .pdf, etc. font partie de la source. Le connector doit être ouvert à d'autres formats de fichiers, pas verrouillé sur XML.
  • Rejouable de 0 — le delta fin est repoussé. v0 : idempotence binaire (vu / pas vu). Un document ré-aperçu à la source déclenche un UPDATE inconditionnel — pas de comparaison de contenu, on assume le re-traitement, couvert par le drop-&-rejoue (§10). Le delta de contenu (n'ingérer que ce qui a réellement changé, via hash ou estampille DILA) est une brique v1, hors chantier v0.
  • Identité par clé canonique allouée. Chaque document reçoit une clé canonique interne (UUID) à l'ingestion. Ré-ingérer le même fichier : ignoré (idempotence par la clé). ELI, ECLI, n° de pourvoi et id source ne sont pas la clé primaire : ce sont des alias réconciliés vers la clé canonique.
  • Le registre d'alias = le manifest. Un registre alias → clé canonique porte à la fois l'identité, le suivi des deltas et la résolution des liens (§7). Il vit dans Neo4j (un node canonique portant ses alias en propriétés) : pas de 4e store à opérer. Il entre dans la saga (§8) et dans le drop-&-rejoue (§10) au même titre que les bases.
  • L'inventaire est lisible — list_known() sur le port. Le registre expose une capacité de lecture de premier rang : énumérer ce qui est su, à côté de resolve/append. Gratuit (une requête Neo4j), et acté dès la v0 bien que le pipeline binaire ne le consomme pas — parce que le mode incrémental v1 en dépendra. Un registre qui sait résoudre un alias sait forcément énumérer ce qu'il contient ; le lui interdire serait artificiel.
  • La découverte = un diff ensembliste, pas de contenu. « Ce qui est nouveau » = source ∖ registre (comparaison de clés, aucun re-hachage). En v0 elle vit dans un node Kedro de diagnostic hors-pipeline (outil d'exploitation : liste le delta, ne modifie rien), consommateur unique tant que le pipeline ré-ingère tout. Pas de service d'orchestration dédié tant qu'aucun run ne consomme la découverte.

Reste ouvert — v1

  • Inventaire auto-découvrant. Au-delà du diff de clés : un système qui découvre et catalogue seul les sources et leurs formes (bases, arborescences, schémas), sans énumération codée en dur. Le port list_known() + le node de diff en sont le socle ; l'automatisation de l'inventaire reste à concevoir.
02

Modèle de document

métier

Pas de typage métier — des champs simples, une différenciation par base.

Doctrine tranchée

  • Pas de typage métier. On abandonne Classification first-class, la vue structurée typée, la hiérarchie de types. Le « type de fichier métier » est un simple champ (doc_type), au même titre que n'importe quel autre. Trop gros refactor, non justifié : l'objectif est de communaliser.
  • Tout ce qui filtre = un champ. Les axes de filtrage (juridiction, statut, formation…) se contentent très bien d'être de simples champs. Pas d'enum global, pas de modèle dédié.
  • La différenciation vit entre les bases. Quand un traitement doit diverger, il diverge Mongo vs Neo4j (texte+méta vs méta+liens), pas dans une hiérarchie de nodes Python.
  • structure supprimé, metadata confirmé. Le structure: dict « vue typée » est retiré. Le texte devient du Markdown (§4). metadata est le fourre-tout légitime des champs plats — confirmé.

Doctrine tranchée

  • Versioning — on casse à volonté. On est en v0 : on peut tout casser, tout le temps, repartir de zéro, tout le temps. Aucune contrainte de migration tant que rien n'est « livrable » (drop & rejoue). Le SCHEMA_VERSION n'est pas un verrou en v0.
03

Parsing

métier

Un parser générique + quelques stratégies enfichables. Il formate aussi vers Mongo vs Neo4j.

Doctrine tranchée

  • Un parser générique + stratégies enfichables. « Un parser par source » est rejeté : c'est l'inverse du but. On factorise la logique de traitement. Les spécificités de source sont des quelques stratégies enfichables (identifiant, titres…), pas des classes séparées ni du pur paramétrage.
  • Le parser a un rôle de formatage. Il reconnaît et structure ce qui va dans Mongo (texte + champs) vs ce qui devient une relation Neo4j. C'est une étape de formatage à part entière.
  • Extraction de liens = code neuf, dans core/links. Le parser LEGI actuel n'extrait aucun lien. La mécanique de liens (§7) est écrite dans un module dédié core/links que le parser importe — il ne la réimplémente pas.

Doctrine tranchée — stratégies = 4 rôles + registre par balise

  • Structure A — « 4 rôles + registre par balise ». Les stratégies enfichables sur la sortie d'analyze() reposent sur une table déclarative dérivée d'analyze() : chaque balise/attribut porte un seul rôle parmi body / link / version / meta. Une stratégie = un handler par rôle. Le rôle est une donnée inspectable, pas du code ; la saturation analyze(corpus_complet) alimente directement la table.
  • Le doc_type ne fait que choisir la table. La mécanique title_mapping[Article/Texte/TexteAdmin] (déjà dans parameters.yml) sélectionne quelle table de rôles s'applique ; elle ne réintroduit pas de typage métier (§2).
  • Golden test = balise sans rôle casse le build. Une balise nouvelle non mappée à un rôle fait échouer un golden test — même dispositif que le catalogue d'events (§12). La saturation réconcilie la table ; rien n'entre en silence.
  • 4 axes de traitement non-standard. Croisés notebooks (juri) × code (LEGI) : (1) texte-corps (title/content → strip HTML + spaCy) ; (2) liens (<LIEN> + @sens/@typelien/@cidtexte → arêtes, pipeline §7) ; (3) versions (date_debut/date_fin/etat → axe temporel — absent de la juri) ; (4) canonicalisation par-type (title_mapping/field_mappings : quelle balise brute devient titre/num/eli). Le reste = aplatissement injectif générique → metadata.
  • Version = stratégie optionnelle, no-op si absente. Le rôle version existe toujours ; 0 balise mappée en juri : le handler ne s'active que si des balises de datation sont présentes. Handlers riches gardent un pipeline interne (structure C locale sous le routage A).

Reste ouvert — saturation

  • Faire tourner analyze(corpus_complet). Le squelette (4 rôles + routage par doc_type) est tranché. Reste à saturer : lancer l'analyse sur les 5 arbres, figer la table rôle-par-balise et son golden test. NB décalage connu : parser.py/parameters.yml/title_mapping sont écrits pour LEGI (TEXTE_VERSION, SECTION_TA), pas pour la juri des notebooks — mappings à réconcilier.
04

Nettoyage & formatage texte

métier

On ingère brut. HTML → Markdown. Normalisation typo, pas de lemmatisation ni de linéarisation.

Doctrine tranchée

  • Sortie = Markdown, balises minuscule. Le parser convertit HTML → Markdown : seules les balises HTML en minuscule sont formatées (h1→#, h2→##, listes -, tables |…). Ce Markdown est le champ _text_ qui va dans Mongo et part à l'embedding. La conversion par balise est le nettoyage.
  • Pas de lemmatisation en v0. Le _clean_text actuel (strip + spaCy lemmatize + lowercase) est remplacé par le convertisseur HTML→Markdown. spaCy sort du chemin critique.
  • Normalisation typographique. On normalise/standardise la typographie : espaces insécables, guillemets, tirets, forme Unicode NFC, casse des abréviations. Fonction pure, isolée, testée unitairement (un golden test entrée→sortie), car elle invalide tous les embeddings si elle bouge. On touche à la forme, jamais au lexique (pas de développement art.→article). Son norm_version entre dans le hash de collection (§6) : un changement de normalisation crée mécaniquement une nouvelle collection.
  • Pas de linéarisation. Tables et listes restent en Markdown ; on ne les linéarise pas en phrases. La linéarisation est un levier d'optimisation à mesurer via le golden set (§10), pas une dette de v0.
05

Chunking

métier

Piloté par doc_type à terme. Découpe propre. Les liens ne touchent pas les chunks.

Doctrine tranchée

  • Granularité pilotée par doc_type. Même chunking partout en v0, mais l'architecture doit permettre de comparer des méthodes de chunking à terme. Les params de chunking (chunk_size, chunk_overlap, frontières) entrent dans le hash de collection (§6) : chaque méthode a sa collection comparable.
  • Chunk = texte pur. Les liens ne touchent pas les chunks. L'extraction des liens est totalement séparée du chunking : deux sorties indépendantes du parser qui ne se croisent jamais au niveau chunk.
  • Champ d'ancrage = source_path. Le structural_path actuel est renommé source_path.
  • Découpe propre. Le chunker consomme du Markdown et découpe proprement aux frontières de titres/sections, pas par taille fixe brute.
06

Embedding

métier

Une stratégie par run. On compare, on ne mélange pas. Qdrant only. Collection nommée par hash de config.

Doctrine tranchée

  • Plusieurs modèles / vues, mais séquentiellement. Oui à plusieurs façons d'embedder — mais une seule stratégie par run. On ne mélange jamais : on compare une méthode après l'autre, pas d'hybride.
  • Une collection par stratégie. Changer de modèle/stratégie = créer une nouvelle collection quand nécessaire. Pas de cohabitation dans la même collection.
  • Qdrant only. On abandonne l'option Mongo-natif pour la vectorisation. Qdrant seulement : plus simple, plus direct, pour contrôler le processus le plus finement possible. EmbeddedChunk reste auto-descriptif (embedding_model, embedding_dim).

Doctrine tranchée — nommage & dérivation

  • Nom de collection = hash pur (façon run-id MLflow). Le nom encode la stratégie via un hash du sous-ensemble sémantique de la config — pas de segments lisibles fragiles. Opacité assumée : elle est levée par le tracking (le run MLflow porte les params en clair). Robuste, sans collision, absorbe n'importe quel paramètre sans réfléchir à l'abréviation.
  • Périmètre sémantique = ce qui invalide les vecteurs. Trois étapes entrent dans le hash : normalisation (norm_version, §4) + chunking (chunk_size, chunk_overlap, frontières, §5) + embedding (modèle, dim). L'opérationnel (URIs, chemins, run_id, owner_id) n'entre pas dans le nom.
  • Dérivation = fonction pure dans core/. config canonicalisée → hash vit dans core/ (pas dans l'adapter Qdrant, pas dans Kedro), à côté de WorkflowConfig. Canonicalisation stricte (clés triées, floats normalisés) & golden test — le hash pur en dépend : même config → même collection, pour toujours. C'est ce hash qui sert aussi de run_id côté tracking (§9).
  • force_drop par-collection. Le drop est scopé à la collection nommée, jamais au store Qdrant entier : deux configs ⇒ deux collections qui coexistent, chacune rejouable indépendamment. Sans quoi l'A/B serait impossible (§10).
07

Liens & relations

métier

Définition mécanique par balise. Extraction brute, résolution en passe séparée ciblée-delta.

Doctrine tranchée

  • Définition mécanique d'un lien. Toute balise portant un attribut de type id/eli dont la valeur est un identifiant ≠ du fichier courant. Le type = le nom de la balise ou un attribut type. Un attribut sens indique entrant/sortant — prérequis, pas optionnel (le voisinage §8bis en dépend).
  • Les autres attributs deviennent des champs. Les autres attributs et la valeur textuelle de ces balises deviennent des champs, comme tout le reste.
  • Module hégémonique = core/links, deux faces. Un seul module au cœur définit tout ce qui touche aux liens : une face extraction (balise → lien brut, appelée par le parser) et une face résolution (unknown → node, appelée par la passe §9). Elles partagent le vocabulaire RelationType. Personne d'autre ne fabrique de lien.
  • Résolution — Option B, ciblée-delta. On ingère tous les liens bruts (cible non trouvée = node unknown), puis une passe séparée (§9) les résout, indépendamment de l'ordre d'ingestion. La passe est ciblée-delta : elle ne re-traite que les unknown que les alias nouvellement arrivés peuvent débloquer (le registre §1 le permet). Résolution = merge intra-Neo4j par le type comme hint et le registre d'alias ; jamais un état spécial UnresolvedReference.
  • RelationType extensible. Le vocabulaire (CITES/MODIFIES/ABROGATES/REFERENCES + casse, vise…) est extensible. Le hint de résolution reste le type.
08

Persistance & responsabilités des bases

métier · archi

Mongo = texte + méta. Neo4j = méta + liens + registre. Qdrant = vecteurs. Saga à compensation systématique. Hors-saga : outils libres.

Doctrine tranchée

  • Répartition. MongoDB = contenu textuel (_text_ Markdown) + métadonnées + autres formats de fichiers. Neo4j = métadonnées + liens/relations + registre d'identité (alias → clé canonique). Qdrant = vecteurs.
  • Transactions distribuées synchrones (SAGA). Les opérations sur les bases doivent être synchrones et atomiques par upload. Si une écriture rate, toutes les autres sont annulées (compensation). Pattern SAGA validé.
  • Non résolus = nodes unknown. Les cibles en attente ne sont pas un store à part : ce sont des nodes/documents de type unknown, dans Neo4j.
  • La saga reste à 3 branches — le reste est libre. L'ancienne règle « pas de 4e store » est réécrite : ce qu'elle protégeait vraiment, c'est de ne pas gonfler la saga de stores de données ingérées à compenser transactionnellement. La saga garde donc ses 3 branches (Mongo/Qdrant/Neo4j). En revanche, hors-saga, on prend les briques dont c'est le métier : le tracking d'expériences (MLflow, §9), la télémétrie (structlog) et tout futur outil d'observabilité sont écrits une fois par run, sans compensation, hors du chemin document-par-document. Ce ne sont pas des « stores » au sens saga. La simplicité se mesure à la clarté des responsabilités, pas au nombre de services.

Doctrine tranchée — mécanique de la saga

Ordre d'écriture arrêté : du store le plus trivial à compenser vers le plus délicat. On termine par Neo4j (le seul non-rejouable), pour ne jouer, en cas d'échec de la dernière étape, que des compensations triviales.

  1. Mongo — upsert texte + méta. Delete-then-insert, idempotent. Compensation → delete du document. Exacte : Mongo n'a pas d'état inter-document.
  2. Qdrant — upsert vecteurs. Delete-by-document puis insert, dans la collection nommée par hash (§6). Compensation → delete_by_document. Exacte, même raison.
  3. Neo4j — nœud + relations + registre, une transaction. Merge du nœud, upsert des relations sortantes, mise à jour du registre d'alias : réunis dans une seule transaction Neo4j (le MATCH des relations exige que le nœud existe → plus de séparation en deux steps). Compensation → défaire exactement ce que la transaction a créé (voir ci-dessous). Étape terminale car la plus délicate à compenser.
  4. Manifest — dans la saga, dernière étape. L'entrée de manifest passe sous protection de la saga (plus hors d'elle) : fermeture de la fenêtre où le process mourait entre saga réussie et manifest non écrit. Compensation → retrait de l'entrée. Le registre étant dans Neo4j, il partage le périmètre de compensation de Neo4j.

Doctrine tranchée — Neo4j compensable & stratégie de rollback

  • Compensation systématique (stratégie A). À chaque échec, rollback complet de tout ce qui a été écrit — pas de roll-forward par replay. Plus propre, plus robuste : la saga garantit la cohérence immédiate, on ne laisse jamais un état partiel se resynchroniser « plus tard ». Ce choix rend la compensation exacte de Neo4j obligatoire, pas optionnelle.
  • Fin du nœud orphelin. Le _noop « le nœud n'est JAMAIS supprimé » est abandonné. Compensation du nœud : DETACH DELETE si aucune relation entrante d'un autre document ne s'y accroche ; sinon dé-hydratation (retrait des seules propriétés posées par ce run, le nœud retombe unknown). Un nœud cible légitime d'autrui n'est jamais détruit.
  • Fin de la sur-suppression de relations. Compenser upsert_relations ne doit défaire que les relations écrites par ce run, pas toutes les sortantes du nœud (qui casserait un état antérieur légitime sur UPDATE). → relations taguées run_id à l'écriture ; la compensation ne supprime que celles de ce run_id.
  • Pourquoi Neo4j est le seul non-rejouable. Mongo/Qdrant n'ont pas d'état inter-document (un doc écrase proprement sa donnée). Neo4j en a : relations entrantes d'autres docs, allocation d'UUID référencée ailleurs, résolutions déjà faites (§7). Rejouer brutalement y détruirait un état légitime — d'où la compensation fine plutôt que le replay.
8b

Recherche itérative & contexte juridique — hors chantier ragcore

métier

Hors périmètre de cette refonte. Vit dans le backend (serving), pas dans ragcore. Consigné ici pour mémoire : concept posé, archi & modèle à modéliser plus tard.

Doctrine tranchée

  • Hors chantier ragcore. Le moteur de recherche itératif n'est pas dans ragcore (ingestion offline) : c'est de la logique de requête live, stateful par session, qui vit dans le backend. Cette section est là pour mémoire uniquement — elle ne pilote aucune décision de la refonte ragcore. ragcore ne fait que préparer les 3 bases qu'il interroge.
  • Évolution assumée du « stateless ». Le stateless du backend était un confort, pas un dogme : la prod autorisera l'état de session.
  • Boucle itérative avec humain dans la loupe. raffiner le prompt en vecteur(s) → recherche Qdrant → score de pertinence relatif à la session → voisinage Neo4j sur les meilleurs → score du voisinage → affichage graphe des sources → fin d'itération. L'utilisateur peut ajuster filtres, pousser la recherche sur de nouveaux vecteurs/fichiers, préciser le contexte : itération à l'infini, avec ré-ajustement systématique des scores en fonction du contexte connu.
  • Score relatif, pas absolu. La similarité cosinus Qdrant n'est qu'une entrée. Le score combine : similarité à la requête raffinée, ancrage au prompt original (anti-dérive), cohérence avec le contexte de session, centralité dans le graphe de voisinage. Re-normalisé à chaque itération.
  • Le voisinage = le rôle serving de Neo4j. C'est ici que se paie le soin mis à l'extraction des liens (§7) : la qualité du voisinage dépend du type et du sens ingérés.

Reste ouvert — à modéliser plus tard

  • Comment les bases « augmentent » la recherche. Le trajet vecteur Qdrant → doc Mongo → voisinage Neo4j est posé ; le pattern exact de scoring reste à modéliser.
  • Contexte juridique normalisé. L'objet accumulateur central de la session : le besoin ancré (prompts + vecteurs raffinés), le jugement accumulé (docs retenus/écartés), le sous-graphe actif scoré, les filtres. « Normaliser » = une forme canonique sérialisable/rejouable/partageable. Analogie : il est au serving ce que le document normalisé est à l'ingestion. À modéliser.
  • Pondération & re-normalisation. Formule exacte des poids et mécanique de ré-ajustement des scores existants au fil des itérations.
09

Orchestration & tracking

métier · archi

Le DAG bi-phasé, ordre enforced par Kedro. Config = objet core/, tracée par MLflow via un port.

Doctrine tranchée

  • Ordre fixe — le DAG bi-phasé. connect → compute_idempotence → ingest_documents → resolve_relations → report, ordre enforced par Kedro (dépendances de nodes). Phase 1 = parse + chunk + embed + persistance des nœuds (saga 3 steps, en parallèle) ; phase 2 = les arêtes, passe ciblée-delta de §7 + promotion des pendantes (§13). Il n'y a pas d'étape « Persist » terminale : la persistance vit dans la saga du worker (§8/§11) — d'où la mort du node persist.py. L'arête ingest_documents → resolve_relations est la barrière (§11) : c'est elle, et non un join(), qui garantit « tous les nœuds avant toute arête ».
  • Idempotence par identifiant. Même philosophie qu'en §1 : rejouer une base ne double rien, la clé canonique pilote insert/skip.
  • Reprise sur erreur par télémétrie. Un échec au fichier 60k : reprise au 60001. Le fichier 60k est loggé et sauvegardé (télémétrie) — le journal de progression sert de point de reprise. (cf. §10.2 : l'erreur est encapsulée, puis corrigée.)

Doctrine tranchée — config de workflow & tracking

  • Config = objet WorkflowConfig dans core/. La config d'un run est un objet ragcore (core/) — c'est lui la référence, c'est lui qu'on hashe (§6). Kedro ne fait que l'instancier (depuis parameters.yml) et l'injecter : parameters.yml n'est qu'une façon de le peupler, pas la vérité. Respecte « ragcore possède ses contrats, Kedro n'est qu'un shell ».
  • Tracking = MLflow, serveur, dès v0. MLflow porte les params en clair (la config §9, qui lève l'opacité du hash §6), le run-id (= le hash qui nomme la collection) et les métriques d'A/B (golden set §10 : recall@k, MRR, nDCG). L'UI de comparaison est disponible tout de suite — c'est le point même de §6/§9. Logging best-effort : si MLflow est indisponible, le run d'ingestion ne casse pas (le tracking est de l'observabilité, pas de la donnée dans la saga §8).
  • Derrière un port ExperimentTracker. WorkflowConfig → log passe par un port ragcore (core/ports/tracker.py : start_run/log_params/log_metrics/end_run), l'outil est un adapter interchangeable (adapters/tracking/mlflow/). Le choix MLflow cesse d'être irréversible : un futur ClearML (extensibilité RAG) ou Aim (UI) = un nouvel adapter, zéro node touché. Brique structurante bon marché actée tôt.

Transversal

métier

Ce qui traverse toutes les étapes. On est en v0. Wicked problem : tout ingérer.

Doctrine tranchée

  • v0 — pas de migration. On est toujours en v0 : pas de contrainte de migration de schéma (drop & rejoue tant que rien n'est livrable).
  • owner_id = fidélité au réel. Les informations sont retranscrites complètement et fidèlement : owner_id = « moi », pas de multi-tenant réel à gérer en v0.
  • Deadcode à épurer. Le node embedding archivé (et autres héritages) est du deadcode : à supprimer, pas à maintenir.
  • Wicked problem — tout ingérer. Philosophie : dans l'absolu, être capable de tout ingérer. S'il y a une raison théorique/pratique pour qu'un élément ne puisse pas l'être, on logge le fichier pour garder une trace. Tout le projet est une itération : l'erreur est encapsulée puis corrigée, jamais présumée impossible. Pas de « cas limite » a priori.

Doctrine tranchée — évaluation

  • Deux golden sets, deux évaluations distinctes. Séparer l'éval projet (ingestion) et produit (recherche). (1) Golden files d'ingestion : entrée XML fixe → sortie attendue figée (Markdown normalisé, champs, liens type/sens/cible) ; non-régression déterministe. (2) Golden set de recherche : (question, docs pertinents attendus) jugés, pour mesurer chunking/embedding/scoring (recall@k, MRR, nDCG). Ses métriques sont loggées dans MLflow (§9) par collection : l'A/B se lit directement dans l'UI. Amorçable petit, grandit itérativement.
  • Le log d'échec alimente le golden set. Chaque fichier loggé comme iningérable (§10 wicked problem) devient, une fois compris, un candidat au golden set. Log d'échec et golden set : deux faces d'un même dispositif de qualité.

Reste ouvert — mesure, pas décision

  • Définition du « livrable ». Le double golden set en pose le socle ; le seuil qui atteste qu'une base est « correctement ingérée » reste à fixer. Ce n'est pas une décision de cadrage en attente : un seuil ne se décide pas à vide, il se lit sur des métriques qui n'existent pas encore. Il se fixera quand les deux golden sets seront peuplés et que MLflow (§9) aura de quoi comparer. Même nature que la saturation (§3) : un travail de terrain, pas un arbitrage.

Concurrence & livraison

archi

Comment le code async tourne sous un orchestrateur sync, comment N documents s'ingèrent en parallèle, et quelles garanties de livraison en découlent. Transverse à toute source.

Pourquoi une famille à part. Kedro est synchrone, les repos (Motor, Neo4j async, Qdrant async) sont async. Le pont entre les deux, le modèle de parallélisme, et la sémantique de livraison qui en découle, sont de l'architecture pure : identiques que l'on ingère LEGI ou de la jurisprudence. Le principe « architecture propre, hypothèses déclarées » s'y applique sans remise à « plus tard ».

Doctrine tranchée — runtime & livraison

  • Modèle d'exécution assumé & encapsulé. Fin de la boucle asyncio globale de module (_LOOP dans utils/async_utils.py, état mutable partagé). Le pont sync↔async devient un objet injecté — un AsyncRuntime derrière un contrat, dont une instance = une boucle + son lot de clients. run_async cesse d'être une fonction-module sur une global : c'est une méthode du runtime courant. Le couplage « les clients async sont liés à leur boucle de création » devient l'unité d'isolation assumée, pas un effet de bord.
  • Contrat de livraison explicite (port). La sémantique d'écriture de l'audit — aujourd'hui fire-and-forget non attendu dans la saga (telemetry/mongo_audit.py : loop.create_task), drainé en fin de run — est un choix nommé derrière un port, pas un effet de bord. Au minimum : référence conservée (pas de GC de task), drain aux frontières. La perte au crash n'est acceptable que si elle est observable — car « le log d'échec alimente le golden set » (§10) suppose que le log survit à l'échec.
  • Cohérence delete-then-insert entre stores. La saga (§8) mélange aujourd'hui un delete Mongo conditionnel (if UPDATE) et un delete Qdrant inconditionnel — deux stratégies d'idempotence dans la même transaction. Le contrat par store est unifié et explicite (renvoi §8 : la mécanique saga y vit, la garantie se décide ici).

Doctrine tranchée — parallélisme inter-documents (worker pool)

L'entre-deux du lock est tranché : on va vers le multi-worker. Mais un multi-worker sans verrou par conception, sous deux invariants.

  • Le parallélisme est inter-documents. L'ingestion d'un document (parse → chunk → embed → persist) est embarrassingly parallel au niveau document. Un pool de N workers traite N documents de front. C'est là qu'est le gain, pas dans la concurrence intra-document.
  • Invariant 1 — isolation stricte par worker. Un worker = un AsyncRuntime = une boucle + son lot de clients + son agrégat local. Rien de mutable n'est partagé. La global _LOOP disparaît ; le drain fire-and-forget devient une responsabilité du runtime (chaque worker draine sa boucle) — ce qui résout le couplage actuel où _drain_pending_tasks mélange les tasks de tous les documents.
  • Invariant 2 — dispatch par clé document. Un identifiant (ELI) donné n'est traité que par un seul worker. Comme chunk_id = {ELI}_{ordinal}, l'interférence inter-saga (deux delete-then-insert concurrents sur le même chunk) n'existe pas : garantie par partition, pas par verrou. La compensation intra-saga de §8 reste suffisante.
  • Agrégats fusionnés, jamais verrouillés. Le threading.Lock de telemetry/aggregator.py est supprimé : chaque worker tient son agrégat local, le pipeline réduit les N agrégats en fin de run (monoïde de fusion associatif). Zéro section critique. RunStats devient mergeable — contrainte de conception écrite noir sur blanc.

Doctrine tranchée — ingestion bi-phasée & barrière

Le « lock » réclamé pour l'ingestion des liens n'est pas un mutex : c'est une barrière de synchronisation entre deux phases. upsert_relations fait MATCH (a) MATCH (b) — si la cible b n'est pas encore dans Neo4j, l'arête tombe dans le vide. On maximise le hit en attendant que tous les nœuds existent.

  • Phase 1 — nœuds, en parallèle. La saga par-document tombe à 3 steps : merge_document_node + Mongo + Qdrant. Les relations sortent de la saga par-document. Chaque worker joue sa saga en isolation (invariants ci-dessus).
  • Barrière — tous les nœuds avant toute arête. On attend la fin de phase 1 pour tous les documents. Ce join() de barrière maximise la probabilité que chaque MATCH (b) de phase 2 trouve sa cible. Ce n'est pas une optimisation cosmétique : sans elle, l'ordre d'ingestion décide silencieusement quels liens existent.
  • Phase 2 — relations en batch, composant dédié. Un nouveau composant application/ (ResolveRelationsService) prend l'union des relations extraites, les écrit en batch, et possède le registre de pendantes (§13). C'est lui, et lui seul, qui porte un éventuel lock applicatif Neo4j — non pour la correction (Neo4j sérialise déjà les écritures de nœuds), mais comme optimisation du deadlock-retry sur nœuds partagés.
  • Le manifest reflète les deux phases. Le targets_written ne peut plus affirmer neo4j « fait » en fin de phase 1 (le nœud existe, pas ses arêtes). La complétude des liens d'un document est un état distinct, réglé en phase 2 — et suivi par §13.

Doctrine tranchée — propriété du pool : Kedro exprime les phases, ragcore possède les workers

Le partage n'est pas un compromis mou : chaque outil fait ce qu'il fait bien. Kedro séquence des étapes et matérialise des dépendances ; ragcore exécute le travail. On n'écrit pas d'ordonnanceur, et on ne détourne pas l'orchestrateur.

  • La barrière est une arête du DAG, pas un join() enfoui. Le pipeline devient explicitement bi-phasé : connect → ingest_documents (phase 1) → resolve_relations (phase 2) → report. La dépendance de données entre les deux nodes est la barrière. Elle cesse d'être une hypothèse d'exécution cachée dans du code applicatif pour devenir une propriété lisible du pipeline — application directe du principe « hypothèse déclarée, jamais implicite ». Le ResolveRelationsService réclamé plus haut est le node de phase 2 : le DAG et la doctrine coïncident.
  • Le pool vit dans le node de phase 1, sous ragcore. Un IngestionRunner (application/) tient N workers, chacun son AsyncRuntime, et distribue les documents par clé (invariants 1 & 2). Le modèle de concurrence est ainsi testable sans Kedro et réutilisable hors Kedro (CLI, service) — il n'est pas prisonnier de l'orchestrateur.
  • Pourquoi pas les runners Kedro. Kedro ne parallélise jamais à l'intérieur d'un node : ses runners parallélisent des nodes indépendants du DAG. Or la boucle sur les documents est dans un node — sur une chaîne, un runner parallèle ne parallélise rien. Il faudrait générer un node par document, donc lire la source pour construire le DAG (inversion de dépendance : l'orchestration dépendrait du contenu ingéré). Rédhibitoire en prime : ParallelRunner est multiprocessing — les clients Mongo/Neo4j/Qdrant injectés en MemoryDataset par les hooks ne sont pas picklables et ne traversent pas la frontière de process. ThreadRunner, lui, ne connaît pas la notion de worker persistant : il ne peut pas donner « une boucle + ses clients par worker », soit exactement l'invariant 1.

Doctrine tranchée — corollaires : fusion des agrégats, fabrique, garantie d'audit

  • Les agrégats fusionnent dans le node, et sortent comme donnée. Pas dans after_pipeline_run : le hook ne voit pas les workers, il ne peut fusionner que ce qu'il voit. Le node de phase 1 réduit ses N RunStats locaux (monoïde) et les retourne en sortie de node — un agrégat est une donnée du pipeline, pas un effet de bord de hook. Effet vertueux : le hook cesse d'être un lieu de logique et redevient du pur câblage (il ne fait plus que finaliser et persister le RunSummary).
  • La télémétrie est injectée comme fabrique, pas comme instance. Avec un pool il n'y a plus un agrégateur mais N : le hook ne peut plus construire une instance unique (backends={"aggregate": self._aggregator} devient faux). Il injecte une TelemetryFactory ; chaque worker appelle build() et obtient sa pile — sa boucle, ses clients, ses backends. L'isolation de l'invariant 1 va donc jusqu'aux backends (jsonl, audit Mongo), et pas seulement jusqu'à l'agrégat. C'est ce qui fait disparaître le verrou au lieu de le déplacer : garder les backends partagés aurait fait réapparaître le threading.Lock ailleurs, sans rien gagner.
  • Audit at-least-once d'emblée. Le port de livraison garantit que l'event est écrit au moins une fois — drain synchrone aux frontières (fin de saga, fin de worker, fin de node), plus de create_task fire-and-forget non attendu. Un doublon est bénin ; une perte ne l'est pas, puisque « le log d'échec alimente le golden set » (§10) suppose que le log survit à l'échec. On ne se paie pas d'at-most-once « tracé » pour économiser un drain.

Télémétrie

archi

Quelle information on capture, comment on la route, et son parallèle avec le reste de ragcore. Le mécanisme est archi ; les events métier renvoient au domaine.

Doctrine tranchée

  • Le routage par registry = jumeau de la table de rôles (§3). EVENT_CATALOG comme source de vérité, un EventBehavior par event_type, fallback par défaut — c'est exactement le pattern « donnée déclarative inspectable » de la table rôle-par-balise (§3). On l'assume comme tel : golden test « event inconnu = échec », symétrique du « balise sans rôle casse le build ».
  • Contrat typé des backends. Fin des clés-strings magiques ("log"/"jsonl"/"mongo"/"aggregate") couplant registry ↔ adapter ↔ hook par convention. Le jeu de backends est un contrat, pas un accord tacite entre trois modules. Les blocs if/try/except dupliqués de RegistryAwareTelemetry sont factorisés.
  • Pas de dégradation silencieuse. Tout basculement de stratégie émet un event. Cas d'école : le fallback structurel → taille-fixe du chunker (chunking.py) bascule aujourd'hui sans rien logger. « Tout ingérer sinon logger » (§10) vaut aussi en mode dégradé : ingérer en aveugle sans trace est interdit.
  • Briques hors-saga, chacune sa sémantique. jsonl + audit Mongo + agrégateur (+ futur MLflow §9) sont les briques hors-saga actées en §8 (écrites 1×/run, sans compensation). La télémétrie est cette catégorie ; ce qu'on route et où vit ici, la garantie de livraison vit en §11 (option 1 : livraison = §11, contenu/routage = §12).
  • Fin du mensonge de comptage des relations. RELATION_UPSERTED émet aujourd'hui count=len(relations) — le nombre de relations tentées, pas réussies : un MATCH (b) raté n'émet rien, la relation est perdue en silence. Nouvel event « relation pendante » — cible absente → la relation part au cache §13, et le fait est tracé. Le compte réussi/pendant devient exact. Symétrie stricte avec « pas de dégradation silencieuse » : une arête différée est une donnée, pas un vide.

Reste ouvert — dérivé de la saturation (§3)

  • Quels events de dégradation manquent au catalogue. Le fallback chunker et la relation pendante (§13) en sont ; la saturation (§3) en fera remonter d'autres. La liste exacte se fige avec la table de rôles — le mécanisme est tranché, seul son contenu attend une mesure. Rien à arbitrer ici : le golden test « event inconnu = échec » garantit qu'aucun event ne pourra entrer en silence, quel que soit ce que la saturation révèle.

Cohérence éventuelle du graphe

archi

Une relation à cible manquante n'est jamais perdue : elle est différée jusqu'à ce que la cible existe. La complétude des liens converge, run après run.

Barrière et cache : le même mécanisme, deux échelles. La barrière (§11) résout les liens pendants intra-run — le document cité arrive plus tard dans la même run, on l'attend. Le cache persistant les résout inter-run — la cible arrive dans une run future, on la retente. Les deux disent la même chose : une arête dont la cible manque est différée, jamais jetée. C'est la couche de persistance de ce qui, en §7/§8, resterait un node unknown sans trace de l'arête qui le vise.

Doctrine tranchée — cache des relations pendantes

  • Store = Mongo meta (MURPHY_META). Une collection pending_relations à côté de l'audit et des run summaries. Chaque pendante : owner_id, source_id, target_id, relation_type, metadata, first_seen_run, last_seen_run. Une pendante est une donnée méta (santé de complétude du corpus), pas une donnée métier.
  • Choisi parce que le graphe est droppé. La doctrine actuelle force_drop: true (§10) efface le graphe à chaque run. Un cache vivant dans Neo4j (arêtes :PENDING) disparaîtrait à chaque drop_all() — donc ne persisterait rien. Mongo meta est découplé du cycle de vie du graphe : il survit au drop. C'est le seul store correct sans forcer une seconde décision (l'abandon du drop).
  • Aucune relation n'est jetée. En phase 2 (§11), toute relation dont le MATCH (b) échoue n'est pas perdue : elle est écrite au cache et l'event « relation pendante » (§12) la trace. Une pendante peut rester pendante indéfiniment (cible hors corpus) — c'est un lien légitime vers l'extérieur, pas une erreur.
  • Rejeu ciblé sur les nouveaux nœuds — la complétude converge. On ne rejoue pas tout le backlog à chaque run : on ne retente que les pendantes dont la cible fait partie des nœuds écrits par la run courante. Une pendante dont la cible n'est pas arrivée cette fois-ci ne peut pas se résoudre — la retenter est un coût pur qui croît avec le backlog. Le ciblé borne le rejeu par la taille du delta, pas par l'historique. Il est la même idée que le list_known() du registre (§1) et que la résolution ciblée-delta de §7 : la troisième occurrence du même motif — on agit sur ce qui a changé, pas sur ce qui existe. Le graphe tend vers sa complétude à mesure que les cibles arrivent, sans que le rejeu ne se dégrade run après run.

Doctrine tranchée — hygiène du cache : pas de TTL, clé complète, union idempotente

  • Pas de TTL, pas d'abandon par ancienneté. Le motif habituel du TTL (« le backlog grossit, le rejeu coûte de plus en plus cher ») n'existe pas ici : le rejeu étant ciblé, il est borné par le delta de la run, jamais par la taille du backlog — une pendante qui dort depuis 200 runs ne coûte rien. Il ne resterait que le coût de stockage : ~200 o par pendante, soit ~200 Mo pour un million — le corpus juridique français n'en produira pas tant. Un TTL serait faux, pas seulement inutile : (a) il confond « non résolue » et « invalide » — un arrêt citant une directive européenne jamais ingérée produit une pendante permanente et correcte, dont la suppression efface une donnée vraie parce qu'elle est vieille ; (b) il casse la convergence — « cohérence éventuelle » signifie si l'on attend assez longtemps, ça converge ; borner l'attente, c'est garantir qu'au jour où le corpus cible arrive, les pendantes purgées ne se résoudront jamais, et en silence (contre §12).
  • Clé = (owner_id, source_id, target_id, relation_type). owner_id est dans la clé, sans exception. Une pendante n'est pas un fait du monde : c'est un trou dans un graphe donné. « Cet arrêt cite cette directive » est universel ; « cette arête me manque » est relatif au propriétaire du graphe. Sans owner_id dans la clé, la promotion de la pendante d'un propriétaire efface celle d'un autre : son arête ne sera jamais écrite, et rien ne le signalera (dégradation silencieuse §12, convergence rompue). C'est du reste le modèle d'adressage uniforme de ragcore — document_repo.get/delete/exists(identifier, owner_id), manifest_repo.last_for_identifier(identifier, owner_id), vector_repo.delete_by_document(identifier, owner_id) : tout ce qui est adressable est adressé par (owner_id, …). Y déroger pour ce seul cache ne simplifierait rien : cela créerait une exception.
  • Écriture = union idempotente, pas remplacement. Si le quadruplet est absent, on l'insère avec first_seen_run ; s'il est présent, on met à jour last_seen_run. Jamais d'empilement : le lien est un fait du document, pas de la run — l'empiler ferait de pending_relations un journal de tentatives, donc un doublon de l'audit (§12), qui fait déjà ce travail. Deux stores pour la même information est précisément la faute que la doctrine combat ailleurs.
  • retry_count abandonné → first_seen_run + last_seen_run. Avec un rejeu ciblé, une pendante n'est jamais « essayée puis échouée » : elle est écrite une fois, puis promue une fois (ou jamais). Un compteur de retries compterait un événement qui ne se produit pas. Les deux estampilles de run, elles, disent quelque chose de réel sur la persistance du lien dans le corpus.

Reste ouvert — v1 seulement

  • Invalidation par disparition du lien source — v1. Une pendante n'est pas invalidée par le temps (cf. TTL), mais elle l'est par la disparition de son lien : si le document source est ré-ingéré et ne produit plus cette citation (article réécrit), la pendante est fausse et doit disparaître. La sémantique correcte est alors le remplacement du jeu de pendantes du document source (même contrat delete-then-insert par clé document que Mongo et Qdrant, §8/§11) — et non l'union. Inutile en v0 : force_drop: true reconstruit tout à chaque run. Ce reliquat s'active à l'abandon du drop — même échéance que le :PENDING in-graph ci-dessous.
  • Évolution v1 — :PENDING in-graph. Le jour où le graphe cesse d'être droppé, un nœud :Ghost + arête :PENDING rendrait le graphe auto-réparant (un MERGE sur le vrai identifiant matérialise le fantôme) et rétablirait une source de vérité unique. Conditionné à l'abandon de force_drop sur Neo4j ; hors v0.

Le cadrage est clos, l'arborescence est arrêtée — place à la migration

Les familles métier sont fermées (le lab §3 est tranché). Les familles d'architecture le sont aussi : §11 sur la propriété du pool (Kedro exprime les phases, ragcore possède les workers), la fusion des agrégats et la garantie d'audit ; §13 sur le rejeu ciblé puis, en rév. 9, sur l'hygiène du cache (pas de TTL, clé complète, union idempotente). Le cadrage ne porte plus aucune décision en attente — ni structurelle, ni de politique. Ne subsistent que deux reliquats v1 explicitement datés (ils s'activent ensemble, à l'abandon de force_drop) et des travaux de terrain — la saturation (§3) et le seuil du « livrable » (§10) — qui ne sont pas des questions mais des mesures à faire tourner.

La suite a désormais deux documents, et il en manque un troisième. Ce cadrage dit ce qui est vrai ; l'arborescence cible dit où chaque décision vit — et s'arrête sur un ordre d'écriture en cinq couches (core → application → adapters → sources → shell Kedro). Ni l'un ni l'autre ne dit comment on va de l'état réel du dépôt à cet état cible : le dépôt d'aujourd'hui a perdu une quinzaine de modules que hooks.py importe encore, et ragcore n'a jamais été committé. C'est l'objet du document d'organisation de la migration, qui doit porter quatre choses que le cadrage n'a pas vocation à porter : l'état des lieux du dépôt réel, l'ordre de bataille (ce qui bloque quoi, ce qui se parallélise), la stratégie de bascule (big-bang vs progressif — « on casse à volonté » autorise le big-bang, il ne l'impose pas), et les critères de fin.

Les chantiers ci-dessous restent la matière de cette migration — ce sont les décisions à traduire en code, pas encore un plan d'exécution :

  1. Écrire le cœur — core/links à deux faces (extraction appelée par le parser, résolution ciblée-delta), le registre d'alias dans Neo4j (resolve/append/list_known), WorkflowConfig + la fonction pure de fingerprint (qui nomme la collection Qdrant et le run MLflow), le port ExperimentTracker + son adapter MLflow, le contrat AsyncRuntime et le port de livraison. Tout en dépend, rien n'en dépend — c'est la première couche de l'ordre d'écriture. §1 §6 §7 §9 §11
  2. Écrire le parser générique + sa table de rôles — sources/generic/ (parser, 4 rôles body/link/version/meta, normalisation pure, HTML→Markdown, chunking aux frontières) ; de sources/legi/ il ne doit rester qu'une table et quatre handlers. C'est la mesure du succès de §3 : une source nouvelle = une table, pas un second parser. §3 §4 §5
  3. Redessiner le DAG en bi-phasé — connect → ingest_documents → resolve_relations → report : la barrière est l'arête entre les deux nodes du milieu, les agrégats fusionnés sortent du node de phase 1, et le hook redevient du câblage. §9 §11
  4. Câbler le worker pool — IngestionRunner dans le node de phase 1 : un AsyncRuntime par worker (boucle + clients + backends via la TelemetryFactory), dispatch par clé document, RunStats mergeables, retrait du threading.Lock ; saga par-doc à 3 steps ; audit at-least-once (drain aux frontières). §11
  5. Poser le cache des relations pendantes — collection pending_relations (Mongo meta), clé (owner_id, source_id, target_id, relation_type) en index unique, union idempotente (first_seen_run/last_seen_run), écriture sur MATCH (b) raté, rejeu ciblé sur les nouveaux nœuds de la run, event « relation pendante » ; ni TTL ni retry_count. §12 §13
  6. Poser le contrat télémétrie — backends typés, golden test « event inconnu = échec », events de dégradation (fallback chunker, relation pendante). §12
  7. Câbler la compensation Neo4j exacte — run_id sur les relations, DETACH-DELETE conditionnel / dé-hydratation du nœud, manifest passé dans la saga. §8
  8. Saturer le lab — analyze(corpus_complet), figer la table rôle-par-balise + golden test. §3

Chantier serving distinct, à modéliser plus tard : le contexte juridique normalisé et le scoring relatif du moteur de recherche itératif (§8bis). Reliquat v1 assumé : l'inventaire auto-découvrant (§1) et le :PENDING in-graph (§13).
